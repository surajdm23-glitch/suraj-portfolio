Rate Module

What is the
Rate Card module?

Understand the module's purpose and structure before following the design walkthrough. The Rate module centralises all carrier and shipper contracts in one place - eliminating manual workarounds and billing leakages.

Eliminate leakages in transportation revenues & costs by managing all contracts in one platform. Leverage analytics to quickly identify discrepancies and high costs in order to constantly and efficiently reduce your costs of delivery and improve your margins.
Module coverage - five areas

The Rate module spans contract setup, party management, rate cards, and proactive alerts. Each area builds on the last.

Sub-areas: Custom vs Default  ·  Transportation Charges  ·  Additional Charges  ·  Volume Discount
05
Set Alert for Rate Expiry

Proactive notifications when rate contracts are approaching expiry - preventing billing gaps and revenue leakage from lapsed contracts before they happen.

01 - Rate Card Rule Logic Builder

What is the
Rule Logic Builder?

The Rule Logic Builder is a self-service ("DIY") configuration tool designed to let users define complex, dynamic rate calculation logic without relying on unscalable custom scripts. It essentially acts as an intelligent wrapper around the core rate engine. The rate engine is just a simple "calculator" - the logic builder allows you to transform data before it goes into the calculator, conditionally filter the requests, and adjust the final output. Crucially, this logic is set up globally for a specific party (carrier or shipper) rather than forcing the user to recreate it for every single billing cycle.

What is Rule Logic builder
The Rule Logic builder is a self-service ("DIY") configuration tool designed to let users define complex, dynamic rate calculation logic without relying on unscalable custom scripts. It essentially acts as an intelligent wrapper around the core rate engine. Rate engine is just a simple "calculator", the logic builder allows you to transform data before it goes into the calculator, conditionally filter the requests, and adjust the final output. Crucially, this logic is set up globally for a specific party (carrier or shipper) rather than forcing the user to recreate it for every single Billing Cycle.

When to use which type of rule / Logic
  • Input Transformation - Use this when your standard data doesn't perfectly match what your rate contract requires. It is used for "If standard data is X, convert it to Y."
  • Rate Request Logic - Use this when certain charges only apply under very specific operational statuses (this is where your "Status basis" comes into the picture).
  • Output Transformation - Use this when you need to calculate charges based on a percentage of the total costs, or when you need to apply overarching discounts.
Input Transformation (Data Prep)
Smart Data Processing
What it does: This section acts as a data translator. It takes raw data coming from standard entities (like a trip or consignment) and modifies it so the rate calculator can read it correctly before any math happens.

How it works (Examples):
  • Date to Day: If standard data only gives a "Trip Start Date," you use this to extract the specific "Day of the Week" so weekend billing can be applied.
  • Custom Combinations: If Location Type is "PUDO" and Consignment Type is "Pickup," you combine them to create a custom "PUDO Pickup" filter.
Rate Request Logic (Conditional Rules)
Establish Conditional Request Logic
What it does: This section acts as a conditional filter. It sets the rules that tell the system which specific charge heads to actually ask the Rate Engine to calculate, based on the real-time status of the order.

How it works (Examples):
Cancellation Rules: If the order Status equals "Cancelled", set the rule to only request cancellation charges from the engine.
Standard Rules: If the order Status does not equal "Cancelled", set the rule to request standard freight, fuel surcharge, and service time charges.
Output Transformation (Post - Cal)
Final Adjustments & financial Overlays
What it does: This section adjusts the final price tag. It takes the completed base calculation returned by the Rate Engine and applies final mathematical adjustments before saving the total to the database.

How it works (Examples):
Applying Taxes: Calculate a 10% tax on the combined sum of the freight charges and the fuel surcharge.
Applying Discounts: Calculate a 5% merchant discount on specific charge heads, or apply a global volume discount.

03 - Problem

Shipping rates are two
unsolved problems, not one

Every carrier and shipper needs a rate contract. That's a known problem. The harder one - transforming raw operational data so the rate engine can actually calculate correctly - was being solved with one-off dev scripts per client, invisible to the product entirely.

Problem 01
Rate contract setup is complex and manual

Each party requires billing zones, charge heads, and rate tables configured individually. Without product tooling, ops teams used spreadsheets and filed backend tickets for every variation.

Problem 02 - Core gap
The rate engine needs clean input. The data isn't.

The rate card API is just a calculator. It takes structured parameters and returns numbers. But raw data from trips, consignments, and enriched events doesn't match what it expects - and nothing in the product bridged this gap.

Previously: one-off custom scripts, written per carrier contract - unscalable, unauditable, recreated from scratch for every new billing configuration change. This was the product's single largest hidden operational debt.
Real carrier examples that defined the scope

Two carrier scenarios that surfaced repeatedly across dev tickets - each one previously required a custom script to solve.

PUDO PickupCustom filter example

In FarEye, Location Type = "PUDO" and Consignment Type = "Pickup" are two separate fields. But a carrier's rate card charges "PUDO Pickup" as a single combined billing zone. The product had no way to create this combination. Input transformation solves it: If location.type=PUDO AND consignment.type=Pickup → set billing_filter="PUDO_PICKUP"

Australia PostMath transformation example

Australia Post charges a "subsequent item quantity" - which is (actual quantity − 1). Standard entities pass the full quantity. But the rate engine must receive quantity minus one. Without input transformation, every carrier with this kind of derived field needs a custom script: item_quantity = actual_quantity − 1

Data arrives from two incompatible sources

Rate calculations run in two fundamentally different contexts - transformation logic must be defined separately for each.

Via carrier location API
Pre-creation (Checkout) - location-centric data, limited fields.
Via enriched events
Post-creation (Consignments) - richer entity data: trip, stop, shipment.
Entity hierarchy - where rates operate

The data model is layered. Rules run at one of three levels - choosing the wrong one produces silent billing failures.

Billing Cycle
└─ Driver
└─ Trip Level 1 · routing, distance, per-leg charges
└─ Stops
└─ Consignment orders Level 2 · weight, volume, COD, handling
└─ Shipments Level 3 · per-shipment charges
04 - Design Strategy

More time in research.
Less in execution.

This wasn't a simple CRUD form. The rate pipeline involves multiple data sources, conditional logic, and domain concepts that ops users don't know upfront. The design process spent disproportionately more time in research and critical thinking than in visual execution.

Domain immersion first

I spent significant time understanding how the rate engine works - what it expects as input, what it returns, and how the data pipeline flows from event to charge. This prevented designing around assumptions that would break in dev.

Mapping the existing approach

I mapped how the custom-script approach worked - what was being transformed, by whom, and why. This created a parity baseline: the product had to absorb everything devs were doing in code before it could replace those scripts.

Approach comparison

Two rule management approaches were evaluated. Approach 2 - faster, matched user mental model despite one friction point on dynamic entry point changes - was chosen.

The core insight: the rate engine is just a calculator. The product's entire value is in the three-stage wrapper - input transformation, conditional charge selection, output adjustment.
Design principles applied to reduce cognitive load

Six principles, each tied to a specific UX decision in the product. Every one came from a real user-research observation, not a style guide.

P1
Progressive disclosure - show complexity in stages

Users never face more than one decision at a time. The rule creation flow gates each step: level selection first, then category selection, then configuration. This directly reduces cognitive load for non-technical ops users who work in billing.

Applied in: Two-step modal flow · Adaptive form per rule type
P2
Make the mental model visible - don't leave it implicit

The three-stage pipeline is not intuitive. It's surfaced explicitly: three kanban columns, three category cards in Get Started, and a dedicated "Know more" modal with a full pipeline diagram. Knowledge transfer was critical - this is a DIY product for users who are new to the concept.

Applied in: Three-column kanban · Know more modal · Get Started picker · Empty state diagram
P3
Constrain before you configure - level gates parameters

The calculation level (Trip/Consignment) is set before rule parameters appear. This prevents impossible configurations - trip.zone doesn't exist in a shipment-level context. Silent failures in billing are the worst outcome.

Applied in: Level selection modal as step 1 · Entity-scoped parameter dropdowns
P4
Separate concerns structurally - not just visually

Input transformation, rate request logic, and output transformation interact with the rate engine at different pipeline points. A merged list allows miscategorisation. Hard structural separation (columns) makes category errors structurally impossible.

Applied in: Three kanban columns · Stage-specific rule type options · Separate + Add per column
P5
Support safe iteration - draft mode and test run

Billing is high-stakes. A misconfigured rule can cascade across an entire billing cycle. Draft mode + snackbar feedback lets teams build incrementally without fear. Test Run validates logic against real data before live billing.

Applied in: Save as Draft · Active/Draft status chips · Test Run button · Kebab menu with Activate
P6
Logic lives at the party level, not per billing zone

A critical UX decision from the Feb 17 session: the transformation logic is the same across all billing zones for a given party. Coca-Cola uses consignment weight everywhere - not consignment weight for North Zone and shipment weight for East Zone. Making users set up the same logic for every billing zone would be a UX disaster. Logic is set up once at the party level and applies globally.

Applied in: Logic tab lives at party/RC level · No per-billing-zone logic overrides in v1

06 - Design Walkthrough

Screen by screen

Every screen exactly as designed and reviewed. Annotations explain the key design decisions behind each element.

01
Party View - Rate Contracts table

Entry point. A party-level table of all carrier and shipper rate contracts. The kebab menu on each row exposes "Add Rate Calculation logic" - the direct path into the logic builder from the party context.

A
Kebab menu shows "Add Rate Calculation logic" as the primary action - directly routes the user to the correct party's calculation logic tab without extra navigation steps.
B
Status tabs (All · Active · Upcoming · Exception) provide instant triage. Exception state surfaces contracts with configuration errors before they affect billing cycle runs.
C
Rate Card type (Global / Custom) is surfaced as a column - determines scoping of the logic rules. Global applies across billing cycles; Custom is party-specific.
02
Empty state - "No Rate rules found" with onboarding

First-time experience for a party with no rules configured. The empty state is educational - it shows a schematic preview of what rules look like, then surfaces "Know more" as the primary CTA. This is critical for a DIY product where users are unfamiliar with the concept.

A
"Know more" as the primary empty state CTA - knowledge transfer was identified as the most critical UX challenge. Users need to understand the three transformation stages before they can configure anything correctly.
B
Schematic rule preview in the empty state (greyed cards with arrows and values) gives users a visual anchor for what they're about to build, reducing anxiety before the first rule creation.
03
Know More modal - full pipeline education

The most important screen for user onboarding. Explains the full pipeline with a visual diagram, a clear breakdown of when to use each type, and three detail cards. This was designed with the insight that without upfront education, users will misconfigure rules between stages.

A
Visual pipeline diagram shows the full data flow: Standard Entities → Input Transformation → Rate API → Output Transformation → Calculated Shipping Charges → DB. Makes the abstract pipeline tangible.
B
"When to use which type" bullet list directly answers the most common user confusion point - the difference between Input (data prep), Rate Request (conditional selection), and Output (post-calculation adjustments).
04
Select Level modal - calculation level gating

Step 1 of the rule creation flow. Users select Trip, Consignment, or both. This is a hard gate - level determines which entity parameters are available in the rule builder. Without this step, users would build rules with inaccessible fields.

A
Large card format with illustration and description - each level has an icon, a card selection state, and a plain-English description. Prevents users from selecting a level they don't understand.
B
"Select both level if rules apply on Trip and Consignment level (Both)" - the info banner removes ambiguity about whether levels are mutually exclusive. This came directly from the review feedback.
05
Get Started modal - choose rule category

Step 2 of the rule creation flow. Shows the three pipeline stages as selectable cards with illustrations. The selected level is shown as a chip at the top, editable via pencil icon. Reinforces the pipeline model every time a rule is created.

A
Level chips shown at top with edit icon - user can go back and change the level without losing their category selection. Progressive flow with full reversibility.
B
Three category cards with mini illustrations - Input Transformation shows a date-to-weekday conversion diagram. Rate Request shows the if-status conditional logic. Output shows a tax/percentage application. Visual examples remove ambiguity.
06
Add Transform Input Rule - side panel with adaptive form

The rule configuration panel. Slides in from the right. The form body is fully adaptive - "Day of the Week" shows source field (dropdown with entity-scoped options + Add new field) → date component → target field. Other rule types show different form structures entirely.

A
Source Field dropdown with entity-scoped options - trip.date, trip.start_date, consignment.date etc. Options are scoped by the level selected in step 1. Vishu requested free text input too - "+ Add new field" at bottom of dropdown handles this.
B
Save Rule as Draft - allows teams to build rules incrementally without making them live. Draft rules appear in the kanban with a Draft badge and a yellow left border, clearly distinct from active rules.
C
Adaptive form body - selecting "Look up from Masters" changes the form entirely. "Add Condition" shows an if/then builder. "Custom Script" shows a code editor with syntax validation. Only relevant fields are shown at any time.
07
Calculation Logic kanban - populated state

The main rule management view once rules exist. Three columns, each with distinct colour accents (blue / purple / green). Rule cards show type chip, logic preview in monospace, applies-on, level, and creation date. Test Run button appears once rules are configured.

A
Rule card detail rows - Logic (monospace colour-coded preview), Applies on, Level, Created date. All metadata visible inline without opening the card. Designed for the 10–12 rules per party use case confirmed in the review.
B
Toggle on each card - active (red/on) or inactive (grey/off). Status change shows a snackbar notification immediately. Draft rules show a Draft badge instead of a toggle.
C
Rule Level chips in subheader (Trip · Consignment) appear after first rule is created. Editable via pencil icon - changing level regenerates available parameters across all rules in this party.
08
Rule card kebab menu - Edit / Duplicate / Delete

On hover, the calendar date icon in the top-left of each rule card transforms into a kebab menu icon. Three actions: Edit Rate Logic (opens the side panel pre-filled), Duplicate and Edit Rule (creates a draft copy), Delete Rule (destructive, irreversible).

A
Hover state changes date icon to kebab - the calendar icon serves a dual purpose: it communicates the rule's creation date by default, and becomes the action trigger on hover. Reduces visual noise when scanning the kanban.
B
Duplicate and Edit Rule - creates a draft copy of the rule immediately and opens it in the side panel. Critical for billing workflows where similar rules apply across charge head variations.

08 - Design Decisions

Aligned in review.
Rationale behind each.

D1
Rule Logic Builder as a dedicated tab within the party-level view

The logic builder lives as its own tab (Calculation logic) within the RC detail view - not a separate page, not cluttered into party details. Interaction flow: Party View → RC Detail → Calculation logic tab. Clean separation with logical context.

D2
Three stages must be visually separated - not mergeable into one list

Input, Rate Request, and Output interact with the rate engine at different pipeline points. A merged list would allow an output tax rule to be placed in the input stage - a silent billing failure that only appears during reconciliation. Column-enforced separation makes misclassification structurally impossible.

D3
Level selection gates the rule builder - step 1, not optional

Calculation level (Trip/Consignment) determines which entity parameters exist. Without level-first gating, users build rules with inaccessible fields. The modal flow enforces this: level → category → configuration. Non-negotiable ordering.

D4
Source field must support free text input in addition to dropdown

BPM (business process management) integrations require custom field names not in the standard dropdown. The "+ Add new field" option at the bottom of the source field dropdown handles this without exposing complexity upfront.

D5
Pipeline education must appear before first rule creation (Know more)

Knowledge transfer is the core UX challenge for a DIY product where the concept (three transformation stages) is new to users. Know more is surfaced as the primary empty-state CTA and as a button in the toolbar once rules exist. Without this, users misconfigure the wrong stage.

D6
VS Code as build environment - HTML handover to dev team

Figma Make used for component generation, VS Code for final build. Designer delivers working HTML to dev as a foundation. Time to measure: Suraj tracks actual time for Rate Calculator frontend vs. standard estimate to build the Figma Make budget case for credits expansion.

D7
Rate card setup and logic setup must happen in parallel - not sequentially

Customers typically have the full rate card and the transformation logic on day one - they receive a PDF or Excel with the complete contract. Forcing them to: (1) set up the rate contract, then (2) come back separately to set up logic would be a poor UX. The design enables both in the same session. Logic rules setup tab is always accessible once a party is created.

D8
Logic is set up globally per party - not per billing zone

The transformation logic for a carrier is party-wide - it doesn't differ between billing zones. Requiring users to configure the same input transformation for every billing zone would create enormous unnecessary duplication. Rules live at the party level and apply across all billing zones for that party.
